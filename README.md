# TrollTrace

Исследовательский инструмент для отслеживания того, как нарративы из атрибутированных российских информационных сетей проникают в чешское информационное пространство: альтернативные медиа, Telegram-каналы, мейнстримные медиа и речь политиков, включая выступления в Палате депутатов.

Проект служит двум целям:
1. **Магистерская работа** по политологии (UJEP): узкий, защищаемый срез данных.
2. **Долгосрочный инструмент** (задел на PhD): широкая платформа мониторинга нарративов.

Разрабатывать нужно так, чтобы ядро закрывало потребности диплома, а расширения подключались модулями, не ломая ядро.

---

## 1. Исследовательский вопрос

**Основной вопрос:** проникают ли нарративы из атрибутированных российских сетей в чешские альтернативные каналы, мейнстримные медиа и парламентский дискурс, через каких акторов и с какой задержкой?

**Уточнение:** не «кто ведёт повестку», а «при каких условиях её ведёт тот или иной тип актора».

**Рабочие гипотезы:**
- **H1.** Новые, событийные нарративы впервые фиксируются в альтернативных каналах и доходят до парламента через популистов и гибридных акторов.
- **H2.** Устойчивые культурные нарративы (евро, евроскептицизм, однополые браки и т. п.) ведут сами политики, а каналы их подхватывают.
- **H3.** Мейнстримные медиа редко бывают первыми, но определяют, станет ли нарратив массовым.
- **H4 (модуль I).** Публичные заявления институтов безопасности связаны с изменением траектории нарратива в других слоях: мейнстрим перенимает рамку заявления, а альтернативная сцена усиливает целевой нарратив или запускает контрнарратив против самого института (backfire). Формулировка описательная: «изменения, связанные с заявлением», а не «влияние» (см. 2.1).

**Теоретическая рамка:** intermedia agenda-setting, political agenda-setting (Walgrave & Van Aelst), hybrid media system (Chadwick).

**Важные ограничения формулировок:**
- Работа **описательная**, причинность не доказывается. Используем формулировку «впервые зафиксирован в корпусе», а не «возник здесь».
- **Собственной атрибуции нет.** Аккаунты и сайты не объявляются «российскими ботами» на основе нашего анализа. Атрибуция берётся только из внешних источников (госорганы, признанные исследовательские организации).
- **Собственного фактчекинга нет.** Посты не помечаются как «дезинформация». Допустимо: внешний рейтинг источника и ссылка на существующее опровержение на уровне карточки нарратива.

| **F. Facebook / Instagram** | Страницы политиков и альтернативной сцены | Meta Content Library (только внутри защищённой среды) | Опционально, зависит от одобрения |
| **G. TikTok** | Политики, альтернативная сцена | TikTok Research API | Опционально, зависит от одобрения |

**Принципы:**
- Каждая платформа — отдельный слой со своей нормализацией. Объёмы между платформами напрямую не сравниваются, сравниваются **траектории** (появление, задержка, пик).
- **Facebook не скрейпим.** Только легальные пути (Meta Content Library, DSA ст. 40). Если их нет, Facebook остаётся задокументированным ограничением.
- Для Meta действует модель «код идёт к данным»: разметка выполняется внутри защищённой среды, наружу выносятся только агрегаты. Архитектура должна поддерживать **импорт готовых агрегатов** без сырых текстов.

### Акторы
- **Политики:** институциональное определение — депутаты PSP, чешские евродепутаты, члены правительства, лидеры партий в период исследования.
  - **Политики без публичной функции** (лидеры непарламентских партий, бывшие политики с собственной аудиторией) тоже отслеживаются: у них есть аудитория, и через них нарративы слоя A вероятнее всего попадают в публичное пространство. Статус политика за ними сохраняется, но отсутствие публичной функции честно помечается (`bez veřejné funkce`) и доступно как фильтр в анализе. Бывшие политики (например, Klaus, Zeman) — тоже политики: потеря функции не исключает из выборки, а помечается (`office_status`).
  - Один человек может занимать несколько функций одновременно (депутат и министр, евродепутат и председатель партии). Функции хранятся с датами и источником.
- **Политические инфлюенсеры:** отдельная категория со своими критериями (охват), не смешиваются с политиками.
- **Гибридные акторы:** формально политики, по коммуникации ближе к альтернативной сцене. Отдельный флаг.
- Частота постов — **не критерий отбора**, а переменная для стратификации (терцили активности × партия × роль).
- Порог минимальной активности для включения фиксируется в конфиге и в методологии.
- **Институциональные акторы безопасности** (слой I): отдельная категория, не смешиваются ни с политиками, ни с медиа. Правила — в разделе 2.1.

### 2.1 Слой I: институты безопасности

**Зачем отдельный слой.** Слои A–E *транслируют* нарративы. Институты безопасности в основном говорят *о* нарративах и угрозах (метауровень). Если смешать их заявления с общим корпусом, позиция «против нарратива X» у BIS окажется в одной корзине с позицией политика, который против X по убеждениям. Поэтому слой I хранится и анализируется отдельно и в общие агрегаты слоёв A–E по умолчанию **не входит**.

**Кто входит.** Органы и должности, для которых безопасность — служебная функция, а не политическая программа:

| Группа | Состав |
|---|---|
| Спецслужбы | BIS, Vojenské zpravodajství (VZ), ÚZSI |
| Кибербезопасность | NÚKIB |
| Министерства (ведомственные каналы) | МВД (в т. ч. отдел гибридных угроз), МО, МИД (стратегическая коммуникация) |
| Координация | Úřad vlády: секретариат Bezpečnostní rady státu, советник по национальной безопасности (если должность существует в период исследования) |
| Силовые структуры | Policie ČR (в т. ч. NCOZ), Armáda ČR / Generální štáb |
| Профессиональные руководители | Директора BIS, NÚKIB, VZ, ÚZSI; начальник Генштаба; президент полиции |

Не входят: Kancelář prezidenta (президент — политическая фигура), парламентские комитеты по безопасности (это слой E), аналитические центры и НКО (их отчёты — внешние источники атрибуции, см. ниже).

**Министры: правило разграничения.** Министр внутренних дел, обороны или иностранных дел одновременно политик (член правительства, партийный политик) и руководитель органа безопасности. Решение — классифицировать **не человека, а канал и роль высказывания**:
- **Ведомственный канал** (пресс-релиз министерства, официальный аккаунт ведомства, ведомственный брифинг) → слой I, актор = **институт**, а не министр.
- **Личный или партийный канал** (личные соцсети, партийные мероприятия, предвыборные выступления, речи в Палате депутатов) → министр остаётся **политиком** в своём слое (C/E/F–H) по общему институциональному определению.
- **Интервью в СМИ** — пограничный случай. По умолчанию министр — политик; если интервью дано в официальном ведомственном формате (брифинг, заявление от имени министерства), то слой I. Решение фиксируется вручную при кодировании события.
- У министров силовых и внешнеполитических ведомств ставится флаг `security_portfolio`, чтобы при анализе можно было отдельно посмотреть их **политическую** коммуникацию и сравнить её с ведомственной.
- Профессиональные (неполитические) руководители служб из таблицы выше всегда относятся к слою I, по любому каналу.
- Правило и спорные решения фиксируются в методологии; смена классификации — через журнал аудита.

**Две роли слоя I, которые не смешиваются:**
1. **Источник внешней атрибуции.** Годовые отчёты и тематические материалы (BIS, МВД и др.) используются для обоснования включения сайтов и каналов в слой A или флагов на акторах (`Source.attribution`). Это метаданные выборки, а не данные анализа.
2. **Актор (событийный слой).** Публичные заявления как события на временной оси для гипотезы H4.

**Единица анализа — событие, а не поток.** Объём слоя мал (единицы материалов в месяц на орган), поэтому траектории по слою I не строятся. Каждое заявление кодируется **вручную** как `InstitutionalEvent`:
- орган, говорящий (институт / профессиональный руководитель / министр в ведомственной роли), канал, дата;
- тип: годовой отчёт / тематическое предупреждение / пресс-релиз / брифинг / интервью / иное;
- **конкретность:** назван ли конкретный нарратив (ID из кодбука) или только общая формулировка («российская пропаганда»). События без конкретного нарратива анализируются отдельно и не смешиваются с конкретными;
- позиция по нарративу и ссылка на первоисточник.

**Источники событий.** Ленты новостей на сайтах органов (RSS, где есть; иначе вежливый скрейп ленты по принципам 4.1) + годовые отчёты + **ЧТК и слой D**, потому что многие ключевые заявления звучат в интервью и на брифингах, а не на сайтах. Только по сайтам событий будет недобор.

**Дизайн анализа (H4): event study.**
- Окна вокруг события (по умолчанию −14 / +14 дней, задаются в конфиге).
- Сравнение с **контрольными нарративами** схожего масштаба и стадии жизненного цикла, которые орган не упоминал (грубый аналог difference-in-differences). Без контроля изменение «до/после» неинтерпретируемо: органы реагируют на уже заметные темы, и спад после заявления может быть регрессией к среднему.
- **Предрегистрация:** окна, метрики и правила выбора контроля фиксируются в методологии до просмотра результатов.
- Исходы по слоям:
  - **D:** подхват заявления, задержка, появление рамки «по оценке BIS/NÚKIB…»;
  - **B/C:** динамика целевого нарратива (затухание или усиление), появление контрнарратива против института;
  - **E:** упоминания органа и заявления в стенограммах, кто ссылается и кто атакует;
  - **A:** реакция атрибутированной сети (вероятно, нулевая — это тоже результат).
- Нарратив «спецслужбы / государство цензурируют» (атаки на сам институт) вносится в кодбук отдельно.
- Причинность не заявляется, как и в остальной работе.

## 3. Нарративы и кодбук

**Тема ≠ нарратив.** «Евро» — тема, «евро разорит чехов» — нарратив. Каждая метка = **нарратив + позиция** (за / против / нейтрально).

Два слоя:
1. **Стабильная таксономия тем** (сверху).
2. **Живой реестр нарративов** (снизу):
   - **Дедуктивная часть:** кодбук из литературы и баз (EUvsDisinfo, Chapel Hill Expert Survey, литература о популизме и евроскептицизме).
   - **Индуктивная часть:** каждый новый релевантный документ модель проверяет на конкретные утверждения, которых нет среди известных нарративов. Похожие утверждения складываются в кластеры прямо в потоке (онлайн-кластеризация, без периодических прогонов архива). Кластер, выполнивший формальное правило, становится **кандидатом** и сразу отслеживается в новых документах. В анализ он попадает только после решения исследователя, не модели (подробно — «Новые нарративы из потока», этап 6).

**Формальные правила добавления нарратива** (параметры в конфиге): минимум N постов от минимум K независимых авторов за окно W.

**Версионность кодбука (обязательно):** у каждого нарратива есть ID, определение, примеры, дата добавления и история изменений. Любое изменение логируется.

**Ретроспективная разметка — только вручную.** Нарративы, особенно узкие, возникают постоянно, и прогонять архив на каждый слишком дорого. Новый нарратив отслеживается с момента появления, а его история — документы кластера, из которого он вырос. Полные тексты хранятся (раздел 6), поэтому архив можно прогнать по отдельному нарративу вручную: например, для нарратива из литературы, добавленного задним числом.

**Метрики жизненного цикла нарратива:** первая фиксация (и в каком слое), пик, скорость затухания, порядок подхвата слоями и акторами.

## 4. Пайплайн обработки (воронка)

Тяжёлые модели не применяются ко всему корпусу.

1. **Сбор:** RSS/sitemap/API → сырые документы. Вежливый краулинг: паузы, robots.txt, user-agent исследовательского бота.
2. **Извлечение текста:** trafilatura для веб-страниц.
3. **Фильтр релевантности (дешёвый):**
   - на уровне подключения: только политические/зарубежные/экономические рубрики;
   - на уровне документа: ключевые слова + сходство эмбеддинга с описаниями нарративов.
   - Нерелевантное **не удаляется**: сохраняются метаданные (дата, рубрика, заголовок) как знаменатель для долей.
4. **Эмбеддинги:** локальная многоязычная модель (multilingual-e5 или LaBSE), считаются **один раз** при поступлении, хранятся в pgvector. Многоязычность важна: Pravda часто — машинный перевод с русского, и это позволяет связывать чешский текст с русским оригиналом без перевода.
5. **Детекция дословных заимствований:** шинглы (5–7 слов) + MinHash + LSH (datasketch). Без перебора всех пар.
6. **Детекция пересказов:** kNN-поиск по pgvector.
7. **Разметка нарративов:** классификатор/сходство с кодбуком на всём релевантном корпусе. LLM — только на отфильтрованных кандидатах (пары высокого сходства, кандидаты в новые нарративы, спорные случаи).
8. **Агрегация:** таблица `author × narrative × week` (число постов, доля, z-оценка). Обновляется инкрементально при каждом сборе.
9. **Валидация:** ручная разметка выборки (≈200+), согласие разметчиков (Krippendorff's alpha), сравнение с автоматикой (precision/recall). Отдельно — валидация детекции заимствований на вручную проверенных парах.

Транскрипция видео (Whisper локально) — опциональный модуль, в первую очередь для Telegram.

### 4.1 Принципы сбора (первый этап разработки)

Сбор — первое, что запускается: RSS не даёт архива назад, каждый день задержки — потерянные данные. Анализ строится потом поверх сырых данных.

- **Не фильтровать жёстко при сборе.** Берём всё из подключённых политических рубрик, отсеиваем на этапе релевантности. Лучше лишнее, чем безвозвратно потерянное.
- **Хранить сырой HTML** рядом с извлечённым текстом (сжатым). Смена парсера или ошибка trafilatura → перепарсинг без повторного скачивания.
- **Два времени:** `published_at` (из источника) и `collected_at` (момент сбора). Если дата публикации не извлеклась, это видно, а не подменяется временем сбора.
- **Дедупликация** по нормализованному URL (без UTM и прочих параметров) и по хэшу текста.
- **Версии статей:** если статья изменилась (другой хэш текста по тому же URL), сохраняется новая версия, старая не затирается. Правки и удаления сами по себе могут быть данными.
- Повторная проверка свежих статей (например, через 24 ч и 7 дней) для фиксации правок; при 404/410 статья помечается как удалённая с датой.

### 4.2 Мониторинг сбора (детекция тихих поломок)

Сайты меняют вёрстку, и сбор может ломаться **тихо**: скрипт работает без ошибок, но приносит пустоту или мусор. Сравнивать страницу целиком бессмысленно (новостная главная меняется каждые минуты), поэтому проверяется **результат сбора**. Четыре уровня проверок, для каждого источника отдельно:

**1. Объём.**
- Для каждого источника считается норма: медиана числа документов в день за последние 14 дней (с учётом дня недели, если у источника выраженный недельный ритм).
- Сигнал: 0 документов за сутки, или объём ниже ⅓ медианы, или RSS-лента не обновлялась дольше порога (настраивается per source; у Telegram-каналов с редкими постами порог больше).
- Ловит большинство поломок.

**2. Качество извлечения.**
- Для каждого документа проверяется наличие заголовка, даты публикации и текста нормальной длины (порог по умолчанию 300 символов, настраивается per source).
- Сигнал: резкий рост доли документов без даты, без заголовка или с коротким текстом относительно нормы источника.
- Сигнал: одинаковый текст у разных URL — типичный признак страницы с куки-баннером, капчей, paywall или ошибкой вместо статьи.
- Сигнал: язык текста не совпадает с ожидаемым для источника.

**3. Контрольные страницы (golden pages).**
- Для каждого сайта 2–3 старые статьи, для которых один раз вручную зафиксирован эталон: заголовок, дата, первые ~200 символов текста.
- Ежедневно они перепарсиваются (из свежего скачивания) и сравниваются с эталоном.
- Сигнал: расхождение — значит, поменялась вёрстка, даже если объём ещё в норме.
- Эталоны редактируются в панели исследователя.

**4. Структурный отпечаток.**
- Если для сайта используются собственные селекторы (а не только trafilatura), на свежих страницах проверяется, что каждый селектор (заголовок, дата, тело, рубрика) вообще находится.
- Сигнал: селектор пропал → тревога сразу, до того как испортится статистика.

**Технические проверки:**
- HTTP-статусы (рост 4xx/5xx), внезапные редиректы (особенно на другой домен или на страницу согласия), признаки капчи/антибота, таймауты.
- RSS: лента пустая, невалидная или не обновлялась.
- Telegram: канал недоступен, переименован или удалён.

**Уведомления и реакция:**
- Все сигналы попадают в **уведомления панели исследователя** (раздел 7.2) и дублируются в **Telegram-бот**, чтобы о поломке было известно в тот же день.
- У сигнала есть уровень (предупреждение / критично), источник, тип проверки, примеры проблемных документов и ссылка на страницу источника в панели.
- Анти-спам: повторные одинаковые сигналы по одному источнику объединяются, пока проблема не закрыта; при восстановлении приходит сообщение «источник снова в норме».
- На странице «Источники» у каждого источника статус здоровья (зелёный / жёлтый / красный), история инцидентов и график объёма по дням.
- Периоды поломок фиксируются в данных (`SourceIncident`): пробел в сборе должен быть виден в анализе и описан в методологии, а не выглядеть как «актор замолчал».

### 4.3 Оценка качества данных документа (1–5)

Каждый документ при сборе (и при каждом перепарсинге) получает **оценку качества данных от 1 до 5**. Она отвечает на вопрос «насколько технически корректно документ собран и извлечён», а **не** о содержании или достоверности.

**Принцип: сначала флаги, потом оценка.** Хранятся отдельные булевы флаги проверок, а оценка выводится из них детерминированными правилами. Одна цифра без причин бесполезна для отладки, поэтому в UI и в БД всегда видно, *почему* оценка такая.

**Флаги проверок документа:**
- `has_title` — заголовок извлечён;
- `has_published_at` — дата публикации извлечена; `date_plausible` — не в будущем и не подозрительно далеко от `collected_at` (с учётом ретро-сбора);
- `date_source` — откуда дата: страница / RSS / метаданные (запасной источник снижает оценку);
- `text_ok` — длина текста не ниже порога источника; `text_short` / `text_empty`;
- `lang_ok` — язык совпадает с ожидаемым для источника;
- `boilerplate_dup` — тот же текст встречается у других URL того же источника (куки-баннер, ошибка, заглушка);
- `blocked_page` — признаки капчи, антибота, paywall, страницы согласия или ошибки;
- `selectors_ok` — все собственные селекторы найдены (если для источника используются);
- `extraction_ratio_ok` — разумное соотношение извлечённого текста к HTML (слишком мало → вероятно, взят не тот блок);
- `incident_open` — у источника в момент извлечения был открыт инцидент, касающийся содержимого (предупреждение / критично).

**Инциденты и оценка (правила q2).**
- **Какие инциденты снижают оценку.** Только «содержательные»: извлечение, заглушки (`boilerplate`), язык, контрольные страницы, селекторы. Падения сборщика, ошибки HTTP, пустая лента, малый объём, внутренняя ошибка и «падение средней оценки» документы, которые всё-таки скачались, не портят. Последнее к тому же создало бы петлю: штраф поддерживал бы сам себя.
- **Перепроверка после закрытия инцидента.** Когда инцидент закрывается, ставится задача перепроверки (Job «kvalita»). Для документов окна инцидента (от суток до открытия до закрытия) она:
  1. заново извлекает текст из сохранённого HTML, без запроса к сайту; изменившийся текст сохраняется новой версией и заново проходит обработку;
  2. URL, отброшенные из-за ошибки извлечения как «тот же текст», собирает заново;
  3. документы с признаками заглушки или капчи скачивает повторно, с соблюдением robots.txt и пауз;
  4. пересчитывает оценки; если они изменились — полностью пересчитывает агрегаты.

  После перепроверки (`rechecked_at`) инцидент на оценку не влияет, остаются только признаки самого документа.
- **Тело статьи.** Если trafilatura берёт соседний блок (лента анонсов вместо короткого поста, как у сети Pravda), текст берётся из schema.org `articleBody` или из `text_xpath` в настройках источника.
- **`boilerplate_dup`** ставится со второго повтора: один повтор — обычно та же статья в двух рубриках.
- **Внутренняя ошибка** (исключение кода или БД) считается текущей, пока после неё не было чистого запуска.
- **Зависшие запуски.** Запуски, оставшиеся «в процессе» дольше блокировки (2 ч) после перезапуска воркера, мониторинг закрывает как упавшие.
- **Лента, запрещённая в robots.txt**, выключается с уведомлением, а не опрашивается повторно.

**Шкала (стартовые правила, настраиваются в панели):**

| Оценка | Значение | Типичные условия |
|---|---|---|
| **5** | Чистый документ | все проверки пройдены, инцидентов нет |
| **4** | Мелкий изъян | дата из запасного источника (RSS/метаданные), нет рубрики, текст чуть короче нормы источника |
| **3** | Заметная проблема | нет даты публикации **или** текст заметно короче нормы **или** открыт содержательный инцидент уровня «предупреждение» |
| **2** | Сомнительный | несколько проблем сразу, язык не совпадает, не найдены селекторы, открыт критичный инцидент |
| **1** | Почти наверняка мусор | пустой текст, `boilerplate_dup` (≥ 2 повтора), `blocked_page` |

**Как оценка используется:**
- **Детекция технических поломок:** на странице источника — график средней оценки и распределения оценок по дням. Резкое падение доли 5 и 4 = вероятная поломка. Это пятая проверка мониторинга (4.2): падение средней оценки источника ниже порога создаёт сигнал.
- **В анализе:** агрегаты по умолчанию строятся по документам с оценкой **≥ 3** (порог в настройках). Для методологии делается **проверка устойчивости**: те же результаты на всех документах и только на ≥ 4. Если выводы не меняются, качество данных на них не влияет.
- **В UI:** бейдж оценки у каждого документа с раскрывающимся списком флагов; фильтр по оценке в списках документов и в режиме «клик по точке графика»; в tooltip графика можно показывать долю документов низкого качества за неделю.
- Документы с оценкой 1–2 не удаляются: они остаются для разбора поломки и перепарсинга.

**Версионность:** у оценки есть `quality_rules_version`. При изменении правил или парсера оценки пересчитываются, старые сохраняются в истории, чтобы было видно, что изменилось из-за правил, а что из-за данных.

## 5. Нормализация

- Основная мера — **доля** постов автора о нарративе за период, не абсолютные числа.
- Дополнительно — **z-оценка относительно собственной истории** автора (детекция всплесков).
- **Предложение и спрос разделены:** что сказано (доля) и какой отклик получено (охват, реакции) — разные переменные, на одном графике не смешиваются.
- Агрегация по **неделям** по умолчанию; для редко пишущих — байесовское сглаживание.
- В UI рядом с долей всегда показывается **абсолютное число** (50% может быть одним постом).
- Знаменатель для медиа — все материалы политических рубрик за период.

---

## 6. Хранение и этика

- **Полные тексты хранятся** в закрытой исследовательской базе (нужны для ретроспективной разметки, валидации и защиты от исчезновения ссылок).
- **Публичный интерфейс** показывает только метки, короткую аннотацию и ссылку на оригинал. Полные тексты чужих статей не публикуются.
- Правовая основа: исключение для text and data mining в научных целях (ЕС, чешское авторское право). Тонкие места уточнить на факультете.
- Собираем только публичное: никаких обходов платного доступа, логинов, закрытых групп.
- **GDPR:** политики — публичные фигуры. Комментарии частных лиц не собираются; администраторы мелких каналов и прочие частные лица псевдонимизируются.
- Нужен план управления данными; уточнить требование этической комиссии UJEP.
- Пометок «дезинформация» на уровне постов и политиков нет (юридический и методологический риск).

## 7. Интерфейс

Приложение делится на две части: **рабочую** (анализ и просмотр) и **панель исследователя** (управление исследованием). Панель доступна только после входа.

### 7.1 Рабочая часть

**Дашборд:**
- **Список акторов** (фильтры: слой, партия, роль, когорта активности, флаг гибридности, поиск по имени). Клик по актору → график его нарративов во времени (доли по неделям).
- **Автоматическая разметка всплесков** относительно нормы актора.
- Tooltip: доля + абсолютное число.

**Режим сравнения (без ограничения числа линий):**
- График должен выдерживать **все активные акторы одновременно — до ~350 линий** по одному нарративу на общей оси времени, плюс группы (партия, все альтернативные каналы, весь мейнстрим, парламент).
- Технически: рендер на **canvas** (ECharts в canvas-режиме, не SVG), данные приходят готовыми из агрегатной таблицы одним запросом, анимации отключаются при большом числе серий. 350 серий × ~26 недель ≈ 9 тыс. точек — для canvas это нормальная нагрузка.
- Чтобы 350 линий читались, а не превращались в шум:
  - по умолчанию линии **тонкие и полупрозрачные**, цвет по слою или партии (а не уникальный цвет на актора);
  - **наведение на линию** подсвечивает её и приглушает остальные; имя актора видно в tooltip;
  - **поиск/выбор в легенде** закрепляет подсветку нескольких акторов поверх общего фона;
  - поверх фона можно включить **линии групп** (медиана/среднее по слою или партии) и полосу разброса (межквартильный размах);
  - легенда при большом числе серий — с прокруткой и поиском, а не плоский список.
- **Альтернативный вид для массового сравнения — тепловая карта** «актор × неделя» (цвет = доля нарратива), с сортировкой по времени первой фиксации, слою или партии. Для 350 акторов это часто читается лучше линий: сразу видно, кто и когда подхватил нарратив. Переключатель «линии / тепловая карта» в режиме сравнения.

**Клик по точке графика → реальные посты/статьи за ней:**
- Работает напрямую, если на графике **до N линий** (N в настройках, по умолчанию 10).
- При большем числе линий клик по фону не открывает посты (иначе каша). Сначала нужно **выбрать/закрепить конкретную линию** (наведение + клик по линии или выбор в легенде), и только тогда клик по её точке открывает посты этого актора.
- В тепловой карте клик по ячейке однозначен (один актор × одна неделя) и работает всегда.

**Прочее:**
- **Карточка нарратива:** определение, версия, дата добавления, первая фиксация, слои по порядку появления, ссылки на внешние опровержения (Demagog.cz, Manipulátoři, AFP Fakty, EUvsDisinfo) при наличии.
- **Просмотр заимствований:** пары текстов с высоким сходством и подсвеченными совпадающими фрагментами.

Графики строятся **из агрегатной таблицы**, не из сырых постов.

### 7.2 Панель исследователя

Отдельный раздел для управления исследованием. Все действия в нём пишутся в **журнал аудита** (кто, когда, что изменил, старое и новое значение) — это часть воспроизводимости для методологии.

**Страница «Акторы»** — динамическое добавление и удаление акторов:
- Добавление вручную (форма) и **массовый импорт из CSV** (например, список депутатов).
- Поля: имя, тип, слой, партия, роль, флаг гибридности, привязанные источники/аккаунты (URL, handle Telegram и т. п.), основание включения (критерий, ссылка).
- **Валидация и защита от дублей:** проверка, что аккаунт или URL ещё не привязан к другому актору; проверка доступности источника при добавлении.
- **Безопасное удаление = архивация, а не удаление из БД.** Актор получает статус «исключён» с датой и причиной. Его документы, метки и история остаются в базе, сбор новых данных останавливается, на графиках он по умолчанию скрыт (но может быть показан фильтром).
- **Периоды включения:** у актора хранится, с какой по какую дату он входил в выборку. Повторное включение открывает новый период, а не затирает старый. Агрегаты и доли считаются с учётом этих периодов, чтобы исключение актора не искажало знаменатели задним числом.
- Добавление актора ставит в очередь задачу **ретроспективного сбора** (насколько позволяет источник) и пересчёта агрегатов.
- Перед необратимыми действиями (если их вообще разрешать) — подтверждение и предпросмотр последствий: сколько документов и меток затронуто.

**Страница «Кандидаты в нарративы»** — очередь на ручное решение:
- Карточка кандидата: автоматически сгенерированное описание кластера, ключевые слова, примеры постов, число постов и **независимых авторов**, окно времени, слои, в которых он появился, ближайшие существующие нарративы по сходству.
- Индикатор, проходит ли кандидат **формальные правила добавления** (N постов / K авторов / окно W).
- Действия: **принять** (создать нарратив с определением и позицией), **объединить** с существующим нарративом, **отклонить** (с причиной), **отложить** (вернётся при росте кластера).
- Принятие запускает **ретроспективную разметку** архива и пересчёт агрегатов; кодбук получает новую версию.
- Отклонённые и объединённые кандидаты не исчезают: история решений хранится для методологии.

**Уведомления:**
- Новые кандидаты в нарративы; резкие всплески у акторов; ошибки сбора (источник недоступен, RSS пуст N дней, сменилась структура сайта); завершение долгих задач (ретроразметка, пересчёт).
- Лента уведомлений в панели + опционально e-mail или Telegram-бот.

**Прочие страницы панели:**
- **Кодбук:** редактирование тем и нарративов, история версий, сравнение версий.
- **Источники:** список подключённых сайтов/каналов/лент, статус сбора, последняя успешная загрузка, объём за период, средняя оценка качества данных и её динамика по дням.
- **Настройки:** пороги (релевантность, сходство, правила добавления нарратива, минимальная активность актора, N для клика по точке), окно агрегации, модели. Изменение настроек тоже версионируется.
- **Валидация:** интерфейс ручной разметки выборки и расчёт согласия.
- **Задачи:** статус фоновых процессов (сбор, эмбеддинги, ретроразметка, пересчёт агрегатов).
- **Журнал аудита.**

**Доступ:** роли минимум «исследователь» (полный доступ к панели) и «наблюдатель» (только рабочая часть, например для руководителя). Публичная версия, если будет, — только рабочая часть без полных текстов.

## 9. Модель данных (черновик)

- `Source` — площадка/сайт/канал: тип слоя, платформа, атрибуция (кем, ссылка на отчёт), внешний рейтинг.
- `Actor` — автор: тип (политик / инфлюенсер / медиа / канал / атрибутированная сеть), партия, роль, флаг гибридности, когорта активности, статус (активен / исключён), основание включения.
- `ActorInclusionPeriod` — периоды, когда актор входил в выборку (с/по, причина включения/исключения).
- `ActorAccount` — привязка актора к источникам и аккаунтам (уникальность аккаунта на уровне БД).
- `Document` — пост/статья/выступление: актор, источник, `published_at`, `collected_at`, URL (исходный и нормализованный), заголовок, полный текст, рубрика, флаг релевантности, метрики отклика, хэш, эмбеддинг (pgvector), MinHash-подпись, статус (активен / удалён у источника).
- `DocumentVersion` — версии документа при правках: текст, хэш, сырой HTML (сжатый), время обнаружения.
- `SourceHealthCheck` — результаты проверок мониторинга по источнику и дню (объём, качество извлечения, контрольные страницы, селекторы, HTTP).
- `GoldenPage` — контрольные страницы источника и их эталонные значения.
- `SourceIncident` — инцидент сбора: источник, тип, уровень, начало/конец, описание; используется и для уведомлений, и для учёта пробелов в анализе.
- `DocumentQuality` — оценка качества документа (1–5), флаги проверок, `quality_rules_version`, время расчёта; история пересчётов сохраняется.
- `Topic` — стабильная тема.
- `Narrative` — нарратив: тема, определение, примеры, статус (кандидат/активный/архив), даты.
- `NarrativeVersion` — история изменений кодбука.
- `Label` — документ × нарратив × позиция, источник метки (модель/человек), уверенность, версия кодбука.
- `ReuseLink` — пара документов: тип (дословно/пересказ/репост/цитата), сходство, подтверждено ли вручную.
- `WeeklyAggregate` — актор (или группа) × нарратив × неделя: n, доля, z, отклик.
- `Debunk` — нарратив × внешнее опровержение (организация, URL).
- `Institution` — орган слоя I: название, группа (спецслужба / киберзащита / министерство / координация / силовая структура), каналы и ленты.
- `InstitutionalEvent` — заявление органа (слой I): институт, говорящий и его роль (институт / профессиональный руководитель / министр в ведомственной роли), канал, дата, тип, конкретность, нарратив (опционально) и позиция, ссылка на первоисточник, связанный `Document` (если есть), кто и когда закодировал.
- `EventWindowResult` — результат event study: событие × нарратив × слой × окно, метрики до/после, контрольные нарративы, версия настроек.
- В `Actor` добавляется флаг `security_portfolio` (министры силовых и внешнеполитических ведомств); в `Document` — поле `speaking_role` (политическая / ведомственная) для пограничных случаев.
- `NarrativeCandidate` — кандидат в нарративы: кластер, примеры, метрики, статус (новый / принят / объединён / отклонён / отложен), решение, причина, кто и когда решил.
- `Notification` — уведомление для исследователя: тип, объект, текст, прочитано ли.
- `Setting` / `SettingVersion` — настройки исследования (пороги, окна, модели) с историей изменений.
- `AuditLog` — журнал всех действий в панели исследователя.
- `Job` — фоновые задачи (сбор, ретроразметка, пересчёт агрегатов) и их статус.

### Пользователи и роли

Все страницы, кроме `/healthz/`, требуют входа (`/accounts/login/`). Роли — группы Django, создаются автоматически после `migrate`:

Журнал только дополняется — UPDATE и DELETE запрещены триггером в PostgreSQL. Для будущих страниц панели — `apps.panel.audit` (`AuditedFormMixin`, `log_change`).

### Сбор данных (этап 3)


По расписанию (Celery beat) каждые 5 минут собираются источники, у которых подошёл `collect_interval_minutes`; раз в час статьи перепроверяются на правки и удаление (через 24 ч и 7 дней); раз в неделю обновляется реестр депутатов. Учитывается robots.txt (RFC 9309), паузы между запросами, сохраняются сырой HTML (сжатый), текст, `published_at` и `collected_at`; дедупликация по нормализованному URL и хешу текста, правки — новые версии. Формат файлов источников — `apps/ingestion/sources/README.md`. Фото акторов лежат в `media/` (не в git); без фото показывается заглушка.

### Мониторинг сбора и качество данных (этап 3.1)

Каждый документ при сохранении и при новой версии получает оценку качества 1–5 с флагами (`apps/ingestion/quality.py`, правила `RULES_VERSION`). Раз в час проверяются объём, качество извлечения, средняя оценка и HTTP/доступность; раз в сутки — контрольные страницы (эталоны задаются в админке). Сигналы открывают `SourceIncident` (повторы объединяются, при восстановлении — «снова в норме»), попадают в `/panel/notifications/` и в Telegram-бот. Статус источников — `/panel/sources/`.

```bash
docker compose exec web python manage.py monitor [--source ID] [--golden]   # разовый прогон проверок
docker compose exec web python manage.py assess_quality [--all]             # (пере)оценка документов
```

Telegram: создайте бота у @BotFather, укажите `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID` в `.env` (без них уведомления только в панели).

### Доработка сбора (этап 3.2)

- **Рамки исследования по рубрикам.** Рубрика берётся со страницы (хлебные крошки JSON-LD и микроразметки, `mrf:sections`, `articleSection`), иначе из ленты. `collector_config.rubrics_in_scope` и `rubrics_out_of_scope` — начала рубрик без учёта регистра и диакритики. По ним вычисляется `Document.in_scope`: True, False, или None, если рубрика неизвестна. Документы вне рамок сохраняются (§4.1), но не входят в знаменатель и в воронку обработки. Списки рубрик в `mainstream.json` — предложение, их утверждает исследователь.
- **Слой A** (`apps/ingestion/sources/attributed.json`): Pravda Česko (RSS) и 42TCen. У 42TCen RSS пустой, а месячные sitemap запрещены robots.txt (`Disallow: /*?*`). Поэтому сбор идёт с титульной страницы и `/archive/` через ленту типа `listing` (ссылки по `listing_link_pattern`). Ретро-сбора нет. У Pravda в `meta.origin_urls` сохраняется первоисточник (обычно Telegram-канал, `origin_xpath`). Язык документа определяется по тексту: атрибут `lang` бывает шаблонным.
- **ČTK — České noviny** добавлены в слой D как агентство-первоисточник.
- **Норма объёма с учётом дня недели.** Есть ≥ 21 день истории и выражен недельный ритм (минимум < ½ максимума)? Тогда объём сравнивается с тем же днём недели, иначе с дневной медианой.
- **Оценка качества при пересчёте** учитывает инцидент, открытый в момент извлечения документа, а не текущий.
- **Страница источника** `/panel/sources/<id>/`: графики объёма (всё и в рамках) и распределения оценок за 30 дней, ленты, контрольные страницы, запуски, инциденты.

```bash
docker compose exec web python manage.py import_sources apps/ingestion/sources/attributed.json
docker compose exec web python manage.py update_scope [--source ID] [--reextract]   # пересчитать in_scope (рубрики из сохранённого HTML)
docker compose exec web python manage.py propose_golden_pages [--per-source 3]      # кандидаты в контрольные страницы — проверить в админке
```

### Политики: функции и реестры (этап 3.3)

Человек может занимать несколько функций одновременно. Функции хранятся в `ActorPosition` с датами и ссылкой на источник. `Actor.role` — автоматическая сводка текущих функций.

**Публичная функция и выборка:**
- Публичные функции: президент, депутат, руководство Sněmovny, евродепутат, член правительства, сенатор, краевая или муниципальная функция (включая старост небольших общин), руководитель органа слоя I.
- **Бывший политик — тоже политик.** Потеря функции (конец мандата, уход из правительства или с поста председателя партии) закрывает функцию, но не исключает актора из выборки. Исключает только исследователь, вручную, с причиной.
- Пометка `Actor.office_status` («současná funkce») пересчитывается автоматически и есть в списке и фильтре админки:
  - `office` — zastává veřejnou funkci;
  - `party_only` — jen stranická funkce, bez veřejné funkce;
  - `none` — bez funkce (bývalý politik nebo veřejná osoba).
- Политики без функции (например, бывшие президенты Klaus и Zeman) вносятся в ручной список с `criterion` и прошлыми функциями (`start`/`end`); `manual_inclusion` отмечает включение решением исследователя.
- У бывших политиков в сводке видна последняя функция: «dříve poslanec PSP; bez veřejné funkce».

**Автоматически найденные местные политики.** Старост, заступителей и прочих местных политиков тысячи, большинство публично не высказывается — перебирать общины не нужно. Вместо этого каждый обрабатываемый документ (`process_documents`, для уже собранных — `discover_actors`) проверяется на явное указание функции:
- распознаются starosta/starostka, místostarosta, primátor, náměstek primátora/hejtmana/starosty, hejtman, zastupitel/zastupitelka — только в именительном падеже, рядом с полным именем (křestní jméno из `apps/actors/data/given_names.txt` + фамилия) и названием общины, города или края: «starosta Sezemic Martin Staněk (…)», «Petr Kubis, hejtman Karlovarského kraje»;
- косвенные падежи, функция без места и без имени — пропускаются: ложное срабатывание дороже пропуска;
- новый человек становится актором-политиком с пометкой `added_automatically` («přidán automaticky»), функцией (краевая или общинная) со ссылкой на документ и цитатой (`ActorMention`, «zmínky v textu»); «bývalý starosta» — функция закрывается датой документа;
- уже известный политик не дублируется: добавляется упоминание, функция — только если её ещё нет;
- актор, исключённый исследователем (например, ошибочно распознанный), снова не включается.

### Обработка: релевантность, эмбеддинги, заимствования (этап 5)

Каждый новый документ (и каждая новая редакция текста) проходит воронку `apps/processing/pipeline.py`. Её раз в 2 минуты запускает beat, работу выполняет отдельный воркер `processor` (очередь `processing`, `-c 1`). Модель грузится один раз. Скорость на CPU ~5 док/с.

1. **Дешёвые фильтры:** пустой текст, оценка качества 1, документ вне сохраняемых рубрик (`in_scope = False`, этап 3.2) → нерелевантен, без эмбеддинга.
2. **Эмбеддинг** `intfloat/multilingual-e5-base` (настройка `embedding-model`): `query: ` + заголовок + первые 2000 символов. Считается один раз на текст и модель (`embedding_text_hash`).
3. **Релевантность:** ключевые слова тем (`Topic.keywords`: начала слов без диакритики, «=nato» — целое слово; ≥2 разных в тексте или одно в заголовке) **или** близость к темам и активным нарративам кодбука ≥ `relevance-threshold`. Нерелевантные остаются в базе как знаменатель. Причина решения, найденные слова и ближайшая тема — в `relevance_details`.
4. **MinHash** (128 перестановок, шинглы по `minhash-shingle-size` слов) и 32 LSH-пояса в `minhash_bands` (GIN-индекс).
5. **Дословные заимствования:** кандидаты LSH → `max(Jaccard, доля шинглов заимствующего текста в оригинале)` ≥ `reuse-verbatim-jaccard`.
6. **Парафразы:** kNN в pgvector, затем центрированная близость ≥ `reuse-paraphrase-cosine`. Если пара уже дословная, парафраз не создаётся.

Связи `ReuseLink` идут от более раннего документа слоя-источника (`reuse-source-layers`, по умолчанию A) к более позднему документу другого слоя в пределах `reuse-window-days`. Порядок поступления не важен. При повторной обработке автоматические непроверенные связи пересоздаются, проверенные вручную остаются.

**Почему близость центрированная.** У e5 косинусы любых двух текстов сжаты в полосу 0,80–0,88, порог по ним не работает. Поэтому из векторов вычитается средний вектор корпуса (`EmbeddingCenter`; пока корпус мал, пересчитывается при каждом удвоении). После этого:
- несвязанные тексты дают ≈0;
- статьи об одном событии, написанные независимо, — 0,75–0,85;
- переработка одного текста — 0,85–0,90;
- копии — 0,9+.

Это калибровка на 3,6 тыс. документах слоёв D и E. Пороги 0,35 и 0,85 выбраны по ней. Для переводов ru→cs из слоя A порог нужно перепроверить, когда появятся данные.

```bash
docker compose exec web python manage.py import_topics [--update]          # стартовая таксономия тем (apps/processing/data/topics.json)
docker compose exec web python manage.py process_documents                 # дообработать очередь
docker compose exec web python manage.py process_documents --all           # пересчёт после смены порогов или кодбука (эмбеддинги не пересчитываются)
docker compose exec web python manage.py process_documents --recenter      # пересчитать центр пространства эмбеддингов
```

Длина очереди — поле `processing_pending` в `/healthz/`.

Под них добавлены темы `bezpecnost`, `volby`, `system`, `historie` (`topics.json`). Любая правка нарратива — новая версия (`NarrativeVersion`).

**Разметка — два шага** (`apps/processing/labeling.py`):
1. **Кандидаты** (дёшево, в воронке обработки): релевантный документ ближе к нарративу, чем `labeling-candidate-similarity` (0,25), или ближе `labeling-cue-similarity` (0,15) и содержит ≥ 2 сигнальных слова. Пороги мягкие: пропуск дороже лишнего вызова. На 286 релевантных документах dev-базы — 166 документов-кандидатов.
2. **Решение LLM** через OpenRouter (`labeling-model`, по умолчанию `openai/gpt-6-luna`): один вызов на документ по всем его кандидатам. Ответ по строгой JSON-схеме: есть ли нарратив, позиция документа (pro / proti / neutrálně), уверенность, дословная цитата-доказательство, **кто нарратив несёт** (автор или цитируемый политик) и обоснование по-чешски.

**Почему не только эмбеддинги.** Близость эмбеддингов ловит тему, а не позицию: выше всего к нарративам оказались обычные новости об Украине и выборах в США. Локальная NLI-модель (mDeBERTa-xnli) не понимает чешского подтекста — фразу «posíláme miliardy na Ukrajinu a naši důchodci si nemohou dovolit topit» она сочла *подтверждением* пользы помощи. Поэтому эмбеддинги только сужают поток, а решение принимает LLM.

**Хранение:**
- `LabelDecision` («rozhodnutí modelu») — все решения, в том числе отрицательные: нужны для валидации (precision/recall) и чтобы повторно не платить. Пустое `present` — кандидат ждёт модель.
- `Label` (origin = model) — только при уверенности ≥ `labeling-min-confidence` (0,5). Менее уверенные остаются решениями для ручной проверки. Ручные метки не трогаются.
- `Label.objects.current()` — метки по текущей версии кодбука; метки старых версий остаются историей.

**Ретроразметка — вручную** (решение 4.11.2026). Правка или добавление нарратива архив не трогает. Метка прежней версии действует, пока документ не оценён по более новой версии (`Label.objects.current()`). Прогон архива запускается действием «Dohledat v archivu» в админке нарративов или командой `label_narratives --retro КОД`. Он создаёт задачу «Zpětné anotování» (`Job`), заново проверяет релевантность документов, отсеянных только порогом близости, ставит кандидатов в очередь и по завершении присылает уведомление.

**Данные и расходы:**
- Тексты публичных статей и постов уходят провайдеру через OpenRouter; в запросе требуются только провайдеры с нулевым хранением данных (`provider.zdr`), которые не обучаются на них (`data_collection = deny`). `require_parameters` не ставится: с ним отсекаются провайдеры Anthropic и OpenAI; ответ модели проверяется кодом. Отметить в материалах для этической комиссии.
- Месячный потолок `labeling-monthly-budget-usd` (5 USD): после него кандидаты ждут, приходит уведомление. Источник цифр — `usage.cost` из ответа OpenRouter.
- Без `OPENROUTER_API_KEY` кандидаты копятся, разметка не идёт.

**Строгое определение нарратива (решение 4.11.2026, кодбук v2, задание `p2`).** Нарратив — конкретное утверждение, а не тема; бывают широкие и очень узкие (одно утверждение об одном инциденте). Нарратив присутствует, только если текст:
- продвигает утверждение (**pro**);
- явно его опровергает или называет пропагандой (**contra**);
- сообщает, что его кто-то распространяет, без оценки (**neutral**).

Противоположная позиция по теме без реакции на утверждение — нарратива **нет** (например, обычная речь в поддержку Украины для «Pomáhat Ukrajině se nevyplácí»). Такие случаи у каждого нарратива перечислены в `stance_guide.absent` («Není narativ»). Иначе «присутствие» мерило бы дебат на тему, а первая фиксация и порядок подхвата слоями (H1, H3) датировались бы обычными речами.

`--compare` прогоняет модели на одной выборке без сохранения: доля «нарратив есть», распределение позиций, попарное согласие, цена и время. Выбор модели — по согласию с ручной разметкой (этап 10), а не только по цене.

**Новые нарративы из потока** (решение 4.11.2026, `apps/processing/novelty.py`, задание `p4`):
1. **Проверка документа.** Каждый новый релевантный документ ставится в очередь проверки (`Screening`). В том же вызове модели, что и разметка его кандидатов, модель перечисляет до трёх конкретных утверждений (`NovelClaim`) в духе нарративов влияния, которых нет ни среди кандидатов документа, ни среди 25 ближайших отслеживаемых нарративов (названия передаются в задании). Каждое утверждение — общая формулировка по-чешски, позиция документа, цитата, носитель. Утверждения с уверенностью ниже `labeling-min-confidence` не сохраняются.
2. **Поиск «конкурентов»** по эмбеддингу утверждения:
   - близко к отслеживаемому нарративу (≥ `discovery-known-similarity`) — утверждение не новое, документ ставится в очередь на решение по этому нарративу;
   - иначе близко к открытому кластеру (≥ `discovery-cluster-similarity`) — утверждение добавляется в него;
   - иначе начинает новый кластер (`NarrativeCandidate`).
3. **Правило добавления:** `narrative-rule-min-posts` документов от `narrative-rule-min-authors` независимых авторов (актор, иначе источник) за `narrative-rule-window-days`. Кластер, выполнивший правило:
   - модель составляет строгую карточку: название, определение, позиции, «Není narativ», примеры, сигнальные слова, тему;
   - создаётся нарратив со статусом «Kandidát» и пометкой «navržen automaticky»;
   - документы кластера получают метки без нового вызова модели — это история нарратива (первая фиксация, слои);
   - приходит уведомление.
4. **Отслеживание.** Нарративы «Kandidát» и «Aktivní» проверяются во всех новых документах. В анализ (агрегаты, H1–H4) идут только активные.
5. **Решение исследователя** — стадия кластера в админке «Kandidáti na narativy»:
   - **přijmout** — нарратив становится активным;
   - **sloučit** — собственный нарратив кластера архивируется, документы кластера ставятся в очередь на решение по целевому;
   - **zamítnout** — нарратив архивируется и больше не отслеживается;
   - **odložit**.
   Решения и отклонённые кластеры сохраняются.

Стоимость: один вызов на релевантный документ, около 0,0007 USD (на dev-базе около 80 документов в сутки — примерно 2 USD в месяц), плюс один вызов на карточку нового нарратива. Документы, пришедшие до этого изменения, на новые утверждения проверяются только вручную: `label_narratives --screen-since ДАТА`.

### Агрегация и нормализация (этап 7)

`apps/analytics/aggregation.py` заполняет `WeeklyAggregate`: актор или группа × нарратив × неделя (понедельник, Europe/Prague) × порог качества.

**Знаменатель** — все документы актора за неделю, включая нерелевантные: это всё, что актор сказал. Исключаются:
- документы вне **периода включения** актора. Исключение актора не меняет прошлые недели, а документы, датированные раньше начала периода, в выборку не входят;
- материалы медиа вне сохраняемых рубрик (`in_scope = False`, §5);
- документы с оценкой качества ниже порога. Считаются три варианта: основной `analysis-min-quality` (3) и проверки устойчивости — все документы (1) и только ≥ 4 (§4.3).

Документы, удалённые у источника, считаются: публикация состоялась.

**Числитель** — документы с действующей меткой **активного** нарратива (`Label.objects.current()`; ручная метка важнее модельной). Нарративы «Kandidát» в агрегаты не входят. Хранятся:
- `n_documents` — нарратив присутствует в любой позиции; основная доля = `n_documents / n_total`;
- отдельно `n_pro`, `n_contra`, `n_neutral`.

**Группы:**
- `layer:X` — слой;
- `party:X` — партия, только слои анализа;
- `all` — все слои анализа, без слоя I.

Доля группы = сумма числителей / сумма знаменателей её акторов, то есть каждый документ весит одинаково.

**z-оценка** считается относительно собственной истории ряда: доля за предыдущие `aggregation-z-window` (12) недель с публикациями, минимум `aggregation-z-min-weeks` (4). Разброс снизу ограничен биномиальной погрешностью доли, иначе первое упоминание после серии нулей давало бы бесконечность.

**Сглаженная доля** = (n + α·m) / (N + α), где m — доля слоя актора в ту же неделю, α = `aggregation-prior-strength` (5). Это байесовское сглаживание для редко пишущих акторов (§5).

**Пересчёт:**
- `update_aggregates` — каждые 15 минут, инкрементально: только пары «актор × неделя», где с прошлого запуска появились или изменились документы, решения модели, метки или оценки качества; затем группы этих недель и z-оценки затронутых рядов;
- `rebuild_aggregates` — раз в сутки, полностью (задача `Job`). Это страховка для изменений без отметки времени: периоды включения, статусы нарративов;
- если изменился набор активных нарративов, пересчёт всегда полный;
- вручную: `python manage.py aggregate [--incremental]`.

На dev-базе полный пересчёт занимает около 3 с (5 тыс. строк).

**API** (`/api/…`, вход наблюдателя или исследователя; графики строятся только из агрегатов):
- `series/?narrative=КОД` — недели и для каждого ряда массивы `n`, `total`, `share`, `smoothed`, `z`, выровненные по неделям (`null` — актор в эту неделю ничего не публиковал). Параметры:
  - `min_quality`;
  - `stance` (`all` / `pro` / `contra` / `neutral`; z для позиции считается на лету);
  - `layer`, `party`, `actor` — каждый можно повторить;
  - `groups` (`1` — вместе с группами, `only` — только группы, `0` — без групп);
  - `excluded=1` — показать и исключённых акторов;
  - `from`, `to`.

  350 рядов × 26 недель отдаются одним запросом к агрегатам (проверяется тестом).
- `documents/?narrative=КОД&week=ДАТА&actor=ID` (или `group=layer:D`) — документы за точкой графика: заголовок, ссылка, позиция, цитата-доказательство, носитель.
- `narratives/` — активные нарративы и доступные пороги качества.

### Рабочая часть: дашборд и сравнение (этап 8)

Страницы `/dashboard/…`, вход наблюдателя или исследователя. Графики строятся только из агрегатов, через `/api/…` (этап 7); рендер ECharts на canvas.

- **Акторы** (`/dashboard/`). Фильтры: слой, партия, роль, когорта активности, гибридность, имя; исключённые акторы показываются по флажку. У актора отмечаются **всплески** — недели последних двух недель с данными, где z ≥ `spike-z-threshold` (2,0).
- **Страница актора.**
  - Доли всех активных нарративов по неделям; ромб — всплеск. В подсказке доля, абсолютное число и z.
  - Переключатели: позиция, порог качества, сглаженная доля.
  - Клик по точке открывает посты: заголовок, ссылка, позиция, цитата, носитель.
- **Сравнение** (`/dashboard/srovnani/`). Один нарратив, все акторы.
  - **Линии:**
    - тонкие и полупрозрачные, цвет по слою или партии;
    - наведение подсвечивает ближайшую линию (до 12 пикселей) и приглушает остальные, подсказка показывает актора, долю, n из N и z;
    - список справа с поиском закрепляет линии поверх фона, у закреплённой линии подпись;
    - поверх фона — медиана и межквартильный размах по слою или партии.
  - **Тепловая карта** «актор × неделя»: сортировка по первой фиксации, слою, партии или имени.
  - **Клик → посты:** напрямую, если линий не больше `chart-click-max-lines` (10). Иначе первый клик закрепляет линию, а клик по точке закреплённой линии открывает посты. В тепловой карте клик по ячейке работает всегда.
- **Карточка нарратива** (`/dashboard/narativy/КОД/`):
  - определение, версия, позиции и «Není narativ», примеры, атрибуция;
  - **жизненный цикл**: первая фиксация, слои по порядку появления, пик доли по всем слоям, первые акторы с позицией pro — по тем же документам, что и агрегаты;
  - доли по слоям во времени;
  - внешние опровержения.
- **Заимствования** (`/dashboard/prevzeti/`). Список пар с фильтрами. Сравнение показывает два текста с подсветкой общих фрагментов: от 5 слов для дословных заимствований, от 3 для парафраз; регистр и диакритика не мешают совпадению. Указывается и доля совпавших слов.

**Проверка на 350 демо-акторах** — в отдельной базе, чтобы не смешивать демо с исследовательскими данными:
```
docker compose exec db psql -U trolltrace -d postgres -c "CREATE DATABASE trolltrace_demo"
docker compose run --rm -e DATABASE_URL=postgres://…/trolltrace_demo web sh -c "python manage.py migrate && python manage.py seed_demo"
docker compose run --rm -p 8001:8000 -e DATABASE_URL=postgres://…/trolltrace_demo -e REDIS_URL=redis://redis:6379/15 web python manage.py runserver 0.0.0.0:8000
```
`REDIS_URL` с отдельной базой Redis обязателен: иначе задачи из демо (пересчёт, ретросбор) уходят в общую очередь, и воркер выполняет их на основной БД по чужим `id`. Сами задачи проверяют тип и статус Job и чужую запись не трогают.
Результаты 4.11.2026, headless Chrome:
- 347 линий × 26 недель рисуются за 0,22 с;
- перерисовка после закрепления — 0,36 с, переключение на тепловую карту — 0,29 с;
- ошибок в консоли нет, на ширине 390 пикселей нет горизонтальной прокрутки.

### Панель исследователя (этап 9)

Раздел `/panel/…` только для роли «исследователь». Каждое действие пишется в журнал аудита: кто, когда, старое и новое значение, комментарий.

- **Акторы** (`/panel/akteri/`):
  - **Добавление формой.** Источник можно выбрать существующий, создать новый или пропустить.
    - Аккаунт или URL, уже привязанные к другому актору, — ошибка со ссылкой на этого актора.
    - Адрес существующего источника нельзя завести как новый.
    - Новый источник проверяется на доступность обычным клиентом сбора: robots.txt, честный user-agent. Недоступность и возможный дубль по имени и партии — это предупреждения: их надо подтвердить флажком.
  - **Импорт CSV** в два шага. Сначала предпросмотр с проверкой каждой строки, затем запись строк без ошибок; перед записью проверка повторяется.
    - Колонки: `name;actor_type;layer;party;is_hybrid;source_url;account_id;account_url;inclusion_criterion;inclusion_reference;start_date`.
    - Кодировка UTF-8 или Windows-1250.
    - Источники должны уже существовать.
  - **Исключение = архивация.** Перед действием показываются последствия: сколько документов и меток остаётся, у каких источников не останется активных акторов.
    - Период включения закрывается, сбор по актору останавливается.
    - Ставится полный пересчёт агрегатов.
    - В журнале — действие «Archivace».
  - **Повторное включение** открывает новый период, который должен начаться позже предыдущего; старые периоды не меняются. Ставятся ретросбор (кроме стенограмм PSP) и пересчёт.
- **Кодбук** (`/panel/kodova-kniha/`):
  - темы и нарративы, правка определения, примеров, сигнальных слов и вводки к позициям;
  - обязательный комментарий к изменению;
  - история версий, пословное сравнение любых двух версий;
  - число действующих меток по версиям;
  - кнопка «Dohledat v archivu» — ручная ретроразметка.
- **Настройки** (`/panel/nastaveni/`): поле значения по типу (число, строка, список через запятую, JSON). Каждое изменение — новая версия с комментарием и историей.
- **Задачи** (`/panel/ulohy/`):
  - Job с прогрессом и длительностью;
  - очереди обработки (документы, кандидаты меток, проверка новых утверждений);
  - ручной полный пересчёт агрегатов, отмена задачи в очереди.
  - Если идёт другой пересчёт, задача ждёт и повторяется.
  - По окончании ручной задачи приходит уведомление.
- **Уведомления о всплесках.** После каждого пересчёта агрегатов: актор × нарратив × неделя за последние две недели, где z ≥ `spike-z-threshold`. Одна неделя — одно уведомление, повторные пересчёты не дублируют.
- Кандидаты в нарративы пока решаются в администрации (этап 6), ссылка есть в панели.

### Валидация (этап 10)

Ручная разметка выборки, согласие разметчиков и сравнение с автоматикой (README §4, шаг 9). Выборки создаются в панели (`/panel/validace/`), размечают их в разделе «Anotace» (`/validace/`).

- **Выборка нарративов** фиксирует текущие версии выбранных нарративов. Разметчики и модель оцениваются по одному и тому же определению; поздняя правка кодбука выборку не меняет.
  - Популяция — документы, входящие в агрегаты.
  - Отбор стратифицирован по тому, что сделала с документом автоматика:
    - модель нашла нарратив — 40 %;
    - кандидат, модель сказала «нет» — 30 %;
    - релевантный, но не кандидат — 20 %;
    - нерелевантный — 10 %.
  - Без нижних страт recall не оценить: позитивы, пропущенные фильтрами, иначе не попали бы в выборку.
  - Недобор маленькой страты отдаётся остальным. У каждого элемента есть вес: размер страты в популяции / число отобранных.
  - Seed фиксирован: те же данные и тот же seed дают ту же выборку.
- **Выборка заимствований:** найденные дословные связи (40 %), парафразы (30 %) и «почти пары» (30 %). «Почти пара» — ближайший по эмбеддингу документ слоя-источника без связи. Она показывает пропуски у порога; её популяция не определена, вес не задаётся.
- **Разметка вслепую:**
  - разметчик не видит ни решения модели, ни чужих ответов;
  - по умолчанию не видит и источник с автором — только заголовок, дату и текст;
  - по каждому нарративу одна категория: «нет / pro / proti / neutrálně»;
  - «нельзя оценить» исключает элемент из расчётов.
- **Эталон** — значение, в котором сошлись все разметчики (не меньше двух), либо решение исследователя по спору. Спор показывает ответы под псевдонимами A1, A2… и решение модели. Решение пишется в журнал аудита.
- **Метрики** (`apps/validation/stats.py`):
  - Krippendorff's alpha, номинальная шкала: по 4 категориям и отдельно по присутствию. Проверена на эталонном примере Криппендорфа (α = 0,743).
  - Доля полного совпадения.
  - Precision, recall и F1 присутствия нарратива: по выборке с 95-процентным интервалом Уилсона и в пересчёте на популяцию с весами страт.
  - Точность позиции, матрица ошибок, разбивка по стратам.
  - Документ без решения модели считается «нарратива нет» — оценивается вся автоматика, включая фильтр релевантности и отбор кандидатов. Решение, которое ещё ждёт модель, исключается.
  - Модели можно сравнивать: фильтр по `model_name` на странице выборки.
- **Экспорт для главы о методологии:**
  - CSV всей разметки в длинном формате (разметчики под псевдонимами, эталон, решение модели);
  - JSON результатов вместе с параметрами отбора;
  - сохранённые отчёты;
  - `python manage.py validation_report ID [--model …] [--json]`.

### Деплой на сервер (этап 4)

Нужен Linux-сервер с Docker (2 vCPU, 4 ГБ RAM, от 40 ГБ диска), домен с A-записью на сервер и открытые порты 80/443.

```bash
git clone … trolltrace && cd trolltrace
cp .env.prod.example .env.prod          # заполнить: домен, секреты, пароль БД, Telegram, пинги
docker compose -f docker-compose.prod.yml --env-file .env.prod up -d --build
docker compose -f docker-compose.prod.yml --env-file .env.prod exec web python manage.py createsuperuser
docker compose -f docker-compose.prod.yml --env-file .env.prod exec web python manage.py import_psp_deputies
docker compose -f docker-compose.prod.yml --env-file .env.prod exec web python manage.py import_sources apps/ingestion/sources/mainstream.json
```

- **HTTPS** — Caddy сам получает сертификат Let's Encrypt для `SITE_DOMAIN`; БД и Redis наружу не открыты.
- **Вход** в проде обязателен (`OPEN_ACCESS=false`): полные тексты — закрытая среда (README §6).
- **Бэкапы** — сервис `backup`: `pg_dump` + фото акторов сразу после старта и ежедневно в `BACKUP_HOUR` (UTC), хранятся `BACKUP_KEEP_DAYS` дней в `BACKUP_DIR`. Копировать каталог и за пределы сервера (rsync / диск факультета).
  Восстановление: `pg_restore --clean --if-exists -d trolltrace backups/db-<дата>.dump` внутри контейнера `db`.
- **Мониторинг сервера** — `/healthz/` проверяет БД, pgvector, Redis и пульс Celery (worker + beat, раз в 5 мин); отвечает 503, если сбор встал. Для тревоги «снаружи» завести две проверки на healthchecks.io (или аналог) и вписать их URL в `HEARTBEAT_PING_URL` и `BACKUP_PING_URL`. Поломки отдельных источников — мониторинг этапа 3.1 (панель + Telegram).
- **Обновление**: `git pull && docker compose -f docker-compose.prod.yml --env-file .env.prod up -d --build` (миграции применяются при старте `web`).
